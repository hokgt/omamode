# omamode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `hokgt.omamode`, an Omarchy bar-widget plugin that switches the laptop between a work mode (local llama.cpp model available) and a gaming mode (model unloaded, Steam running), with a panel, a CLI, a Steam launcher guard and a pi extension.

**Architecture:** All logic lives in one bash CLI, `bin/omamode`, split into focused `lib/*.sh` files; it talks to the llama.cpp router over HTTP, keeps runtime state in `$XDG_RUNTIME_DIR`, and runs long operations as detached jobs. The QML panel, the Steam launcher entry, notification buttons and the pi extension are thin clients that call `omamode` with argv arrays and read its JSON.

**Tech Stack:** bash 5 + jq + curl + flock + setsid; Quickshell 0.3 QML with Omarchy `qs.Ui` / `qs.Commons`; TypeScript pi extension (pi 1.6, run under node 26 type-stripping for tests); python3 for the fake router used in tests.

**Spec:** `docs/superpowers/specs/2026-11-22-omamode-design.md`

## Global Constraints

- Plugin id `hokgt.omamode`; installs to `~/.config/omarchy/plugins/hokgt.omamode/`; manifest at repo root with `schemaVersion: 1` (number), `kinds: ["bar-widget"]`, `entryPoints.barWidget: "Panel.qml"`, `barWidget.defaultSection: "right"`, `allowMultiple: false`.
- No symlinks anywhere in the repo (Omarchy refuses plugin folders containing them).
- Nothing writes inside the plugin folder at runtime (any write hot-reloads the plugin). Runtime state: `${XDG_RUNTIME_DIR}/omamode/`. Config: `${XDG_CONFIG_HOME:-~/.config}/omamode/config.json`. Logs: `${XDG_STATE_HOME:-~/.local/state}/omamode/`.
- Never edit anything under `/usr/share/omarchy/`.
- Commands are run with argv arrays (QML `Process.command`, `Util.execArgv`, `pi.exec`, `omarchy-notification-send --action <label> <program> [args]`); never build shell strings from model names or other input.
- Wait limit before unloading while a request is in flight: **120 s** (config `wait_timeout`), polled every **2 s**.
- Steam close timeout: **30 s**. Never force-kill Steam.
- Only one model loaded at a time; omamode always unloads before loading.
- After a reboot: work mode, no model loaded, no activity (guaranteed by keeping state in `$XDG_RUNTIME_DIR`).
- Switching to work mode never loads a model. Nothing loads unless the user presses Load or accepts the pi prompt.
- Notifications with choices use `omarchy-notification-send` with at most **3** `--action` buttons.
- Exact user-facing copy fixed by the spec:
  - `Gaming mode: model unloaded, opening Steam.`
  - `Work mode: Steam closed.`
  - `Steam is available in gaming mode` (button `Switch to gaming mode`)
  - `A game is running. Close Steam and the game?` (buttons `Close and switch`, `Cancel`)
  - `Steam did not close; still in gaming mode`
  - `Waiting for pi to finish…`
  - Too-big: `<model> needs ~<N> GB; the GPU limit is <M> GB` (N and M rounded to whole GB)
  - 2-minute prompt buttons: `Stop the model now`, `Keep waiting`, `Cancel`
- Licence MIT. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Test seams (environment variables every lib reads, so tests never touch the real system): `OMAMODE_HOME` (base for `~` paths), `OMAMODE_RUNTIME_DIR`, `OMAMODE_SERVER_URL` (default `http://127.0.0.1:8080`), `OMAMODE_DRM_DIR` (default first `/sys/class/drm/card*/device` with `mem_info_gtt_total`), `OMAMODE_STEAM_BIN` (default `/usr/bin/steam`), `OMAMODE_HYPRCTL` (default `hyprctl`), `OMAMODE_NOTIFY` (default `omarchy-notification-send`), `OMAMODE_PI_DIR` (default `~/.pi/agent`), `OMAMODE_FOREGROUND=1` (run jobs inline instead of detached), `OMAMODE_POLL=0.1` (poll interval override).

## Review Focus

1. **Model folder contents that are not models** (`mmproj-*.gguf`, `mtp-*.gguf`, `dflash-*.gguf`, split shards `*-00002-of-00003.gguf`, model subfolders) must not appear as separate models, and a subfolder model must be listed once under its folder name. Test in Task 2.
2. **A server started by someone else in single-model mode** (no `/models` route, or `/models` returning 400/404) must give a clear `status` error ("llama-server is not in router mode"), not crash the panel or the job. Test in Task 2.
3. **Two operations at once** (double-click Load, or Gaming while a Load runs) must refuse the second with `Another omamode operation is running` and leave the first untouched. Test in Task 4.
4. **Already-there states:** `gaming` when Steam is already running, `work` when Steam is not running, `unload` with nothing loaded, `load` of the already-loaded model must each succeed as no-ops with a short message. Tests in Tasks 4 and 5.
5. **pi's `settings.json` missing, unreadable or not valid JSON** must never be overwritten; `default` still succeeds for omamode and prints `pi settings not updated: <reason>`. Test in Task 6.

## Shared Interfaces

These are fixed here so every task uses the same names.

**`omamode status --json`** prints one object:

```json
{
  "mode": "work",
  "activity": "idle",
  "detail": "",
  "error": null,
  "server": "running",
  "loaded": {"id": "Qwen3.6-35B-A3B-Q4_K_M", "sizeGB": 22.1},
  "default": "Qwen3.6-35B-A3B-Q4_K_M",
  "gpu": {"limitGB": 65.2, "usedGB": 24.9},
  "steam": false
}
```

`mode`: `work|gaming`. `activity`: `idle|waiting|unloading|loading|restarting-server|starting-steam|closing-steam`. `server`: `running|stopped|not-router`. `loaded`: object or `null`. `error`: last failed operation's message or `null` (cleared when the next operation starts).

**`omamode models --json`** prints an array, sorted by id:

```json
[{"id": "Qwen3.6-35B-A3B-Q4_K_M", "sizeGB": 22.1, "default": true, "loaded": true, "fits": true, "known": true}]
```

`known`: the running router lists it (false means a restart is needed before it can load; Load handles that).

**Exit codes:** 0 ok, 1 operation failed (message on stderr and in `state.error`), 2 usage error, 3 refused (lock held, wrong mode, too big, user cancelled).

**lib function names** (bash, all prefixed `om_`): listed in each task's Interfaces block.
